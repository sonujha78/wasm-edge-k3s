# Findings

Everything below was measured on one machine. Raw data: `bench/results/`, generated tables: [results.md](results.md),
raw evidence: `docs/evidence/`. Charts are generated by `bench/make_charts.py`.

**Environment:** single-node K3s v1.36.4 on Ubuntu 26.04.1 (x86_64, 12 CPUs, ~14 GiB RAM, also running a desktop session),
containerd 2.3.x, containerd-shim-spin v0.25.1 (Spin 4.0.1 runtime), Spin SDK 6.0.0, Rust target `wasm32-wasip2`.

**Workloads:** three implementations of the same three endpoints (`/healthz`, `/`, `/echo`):

| Name in charts | Implementation |
|---|---|
| WASM (Spin) | Rust + Spin SDK 6, one 176 KiB `.wasm`, run by the Spin shim via RuntimeClass `wasmtime-spin-v2` |
| Rust container | Rust std only, thread per connection, keep-alive, static musl binary in a `scratch` image (best case for a container) |
| Python container | Flask + gunicorn (1 worker, 2 threads) on `python:3.13-slim` (a typical container) |

## Summary

| Question | Result on this setup |
|---|---|
| Does WASM start faster than a container? | **Yes at the runtime level** (35 ms vs 150 ms vs 306 ms). **Not measurably at the Kubernetes pod level**: all three take ~570-580 ms to reach Running. |
| Does it scale from zero faster? | **No, it was the slowest** (median 2.0 s vs 1.25 s Rust vs 1.76 s Python), mainly because of the time between Running and Ready. |
| Does it use less memory? | **Versus Python: less at idle (cgroup ~10x, total PSS ~26%), about equal under load. Versus a static Rust container: 4-10x more.** |
| Does it fit more workloads per unit of hardware? | **Versus Python, yes** (64 vs 10 pods under a 512Mi quota; ~1.5-3x by measured host RAM). **Versus static Rust, no.** |
| Does it run unchanged on another architecture? | **Yes, same sha256 on emulated arm64**, but the runtime itself is per-architecture. |

## 1. Cold start

### Without Kubernetes (launch to first HTTP 200, median of 10)

| Workload | Median (ms) | Min | Max |
|---|---|---|---|
| WASM (`spin up`) | 34.6 | 30.9 | 39.5 |
| Rust container (`docker run`) | 149.6 | 125.0 | 165.6 |
| Python container (`docker run`) | 305.5 | 304.0 | 336.5 |

![runtime cold start](charts/1-runtime-cold-start.png)

Caveat: not perfectly symmetric. `spin up` includes process start, Wasmtime init and component compile; `docker run` includes the daemon round trip and runc.
Treat this as "roughly 4x and 9x", not exact ratios.

### On K3s, scale 0 to 1, image already pulled (median of 10)

| Workload | Running (ms) | First 200 (ms) | Ready (ms) |
|---|---|---|---|
| WASM (Spin) | 577 | 581 | 905 |
| Rust container | 565 | 566 | 575 |
| Python container | 579 | 798 | 979 |

![k8s cold start](charts/2-k8s-pod-cold-start.png)

- ~570 ms of Kubernetes pod creation (scheduling, sandbox, CNI, kubelet status sync) is paid by every workload and hides the runtime difference.
- After the pod is Running, the gap to the first served request is about 4 ms (WASM), 1 ms (Rust), 219 ms (Python), derived from the medians above.
- WASM's Ready is ~330 ms later than its first 200. Every WASM pod produced one `Readiness probe failed: connection refused` event; the container pods did not (`docs/evidence/wasm-readiness-probe-events.txt`).
  Working explanation (not proven): kubelet's first probe fires before Spin has bound its port, and the next probe comes later.

## 2. Memory and throughput

| Workload | Phase | cgroup working set (MiB) | Total PSS incl. shim (MiB) |
|---|---|---|---|
| WASM (Spin) | idle | 4.21 | 42.36 |
| WASM (Spin) | light load | 24.99 | 62.65 |
| Rust container | idle | 1.03 | 6.52 |
| Rust container | light load | 1.41 | 6.64 |
| Python container | idle | 41.11 | 57.04 |
| Python container | light load | 42.89 | 58.50 |

![memory](charts/4-memory.png)

Light load = `wrk -t2 -c20 -d30s` against `/healthz`.

| Workload | Requests/sec | p50 | p99 |
|---|---|---|---|
| WASM (Spin) | 11,626 | 1.62 ms | 4.60 ms |
| Rust container | 286,817 | 45 us | 113 us |
| Python container (1 worker, 2 threads) | 2,765 | 7.09 ms | 13.38 ms |

- The pod cgroup shows only ~4 MiB for WASM, but total PSS including the shim processes is ~42 MiB. Kubernetes limits and `kubectl top` see the small number; the host pays the bigger one.
- Under load the WASM cgroup working set grew from 4 to 25 MiB. It is not a requirement: the pod served ~10.7k req/s under an 8 MiB limit (section 4). Exact reason for the retained memory not verified.
- The throughput gap versus native Rust (~25x) is the price of per-request instance isolation and WASI-HTTP marshalling. The Python figure depends on its worker config and is not a tuned result.

## 3. Scale to zero (KEDA HTTP add-on)

KEDA HTTP add-on with `InterceptorRoute` + `ScaledObject` (minReplicaCount 0, cooldownPeriod 15 s, pollingInterval 5 s).
The client sent one request to the interceptor's ClusterIP after the workload had reached 0 replicas. Median of 8.

| Workload | Request to response (ms) | KEDA scaled | Pod Running | Pod Ready | Warm request via interceptor |
|---|---|---|---|---|---|
| WASM (Spin) | 2015 | 691 | 1512 | 2258 | 1.4 |
| Rust container | 1246 | 459 | 1326 | 1395 | 0.8 |
| Python container | 1762 | 518 | 1401 | 2058 | 1.3 |

![scale from zero](charts/3-scale-from-zero.png)

- Requests were held by the interceptor during scale-up and all returned 200; no request was dropped.
- The three workloads reach Running within ~200 ms of each other. The spread in total time comes from the Running-to-Ready step.
- The "KEDA scaled" difference (691 vs 459 ms) should not depend on the workload; with n=8 and WASM running first, treat it as noise.
- KEDA + HTTP add-on itself used ~173 MiB and ~60 mCPU across 10 pods (`docs/evidence/keda-overhead.txt`), with default chart replicas.
  On a 512 MiB edge budget that machinery is larger than the workloads it scales.

## 4. Constrained edge simulation

Done inside the same cluster with pod memory limits and a ResourceQuota, not a 1 vCPU / 512 MB VM (K3s's own control plane would not leave a meaningful budget).

### Minimum memory limit (light load, `wrk -c20 -d15s`)

| Limit | WASM (Spin) | Rust container | Python container |
|---|---|---|---|
| 4 MiB | runs, but only 261 req/s | 253,925 req/s | OOMKilled (crash loop) |
| 8 MiB | 10,658 req/s | 256,404 req/s | OOMKilled |
| 16-32 MiB | not tested | not tested | OOMKilled |
| 48 MiB | not tested | not tested | 3,135 req/s |
| 64 MiB | not tested | not tested | 3,485 req/s |

Effective minimum: WASM 8 MiB, Rust container 4 MiB or below (not tested lower), Python container 48 MiB.
The "PASS" at 4 MiB for WASM is a degraded run (~2% of normal throughput), not a healthy one.

### 512Mi ResourceQuota (requests.memory = limits.memory = 512Mi), scaled to 200 replicas

| Workload | Pod limit | Quota math | Ready | Host RAM used | Per pod (host) | Per pod (cgroup) |
|---|---|---|---|---|---|---|
| WASM (Spin) | 8 MiB | 64 | 64 | 627 MiB | 9.8 MiB | 4.2 MiB |
| Rust container | 4 MiB | 128 | 95 | 673 MiB | 7.1 MiB | ~0 MiB |
| Python container | 48 MiB | 10 | 10 | 312 MiB | 31.2 MiB | 39.2 MiB |

![edge quota density](charts/5-edge-quota-density.png)

- Under the same quota, WASM fit 6.4x more pods than Python.
- The quota only counts pod cgroups. 64 WASM pods cost ~627 MiB of real host RAM, more than the 512 MiB the quota implies, because shim processes sit outside the pod cgroup.
- Measured host RAM per WASM pod is roughly 10-20 MiB (9.8 MiB average at 64 pods, 13.5 MiB at 40 pods, ~20 MiB slope between N=20 and N=40; `MemAvailable` noise is about +-100 MiB).
  That is roughly 1.5-3x denser than Python and roughly 1.5-2.5x less dense than the static Rust container.
- The Rust container stopped at 95 Ready pods although quota math allows 128. Consistent with the node's pod limit: capacity is 110 pods (`docs/evidence/node-max-pods.txt`) and roughly 15 other pods (kube-system, KEDA) were already running, so 95 is a lower bound for the Rust container. The scheduler event was not captured, so the cause is not directly confirmed.
- The raw sweep is in `results.md`; rows with small N are dominated by measurement noise.

## 5. Portability

Evidence: `docs/evidence/part7-portability.txt`.

- The same `wasm_echo.wasm` (179,686 bytes, sha256 `977328a1...295a`) ran on an aarch64 Spin 4.0.1 runtime, with an identical hash on both sides, no rebuild.
- The container needed a second build for arm64 (167 s under emulation). The existing amd64 image was refused on arm64 (`no matching manifest for linux/arm64`).
  Native binary sizes were similar (455,328 bytes amd64, 462,992 bytes arm64).
- Limits of this test: arm64 was **emulated (QEMU)** on an x86_64 host, so it proves "the same binary runs", not performance. The Spin runtime had to be downloaded separately for aarch64.
  It ran in Docker, not through the K3s shim on an ARM node.

## 6. Limitations of these measurements

- One machine, shared with a desktop session; `wrk` ran on the same host as the workloads.
- Small samples (10 cold starts, 8 scale-from-zero runs), medians reported. Occasional outliers (for example 1.1-1.5 s pod starts) were not investigated.
- Workloads are tiny echo services. Results say nothing about heavier applications, and nothing about services that need filesystem, threads, or long-lived state.
- Order effects were not randomised (WASM ran first in each script).
- Memory accounting is approximate (PSS with shared pages, `MemAvailable` deltas). Shim memory attribution per pod was not isolated.
- The Python container uses one worker; a tuned deployment would trade memory for throughput.
- Scale-from-zero was measured through the KEDA interceptor directly, not through Traefik.

## 7. Corrections made along the way

- The first throughput comparison was invalid: the Rust server closed every connection. Fixed in `container-echo:v2` (keep-alive); the first run is kept in `bench/results/baseline/`.
- The first "idle" WASM memory reading was taken from a pod that had already served load; `memory.py` now restarts the workload first (`bench/results/run3-fresh-idle/`).
- The first memory-limit verdict (`rps > 0`) was too lenient; the 4 MiB WASM run is reported as degraded.
